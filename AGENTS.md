# AGENTS.md

This file guides agentic coding assistants working in this repository.
It summarizes how to build/run, the expected coding style, and any repo rules.

## Repository overview
- Primary language: Python (>=3.9).
- Code lives in `src/` with scripts in `scripts/`.
- Configurations are in `configs/`, data in `data/`, results in `results/`.
- Figures and schematics are generated by scripts in `scripts/`.
- Docs are in `docs/` (see `docs/plasticity_transfer_model.md`).

## Build, install, and environment
- Build system: Hatchling (`pyproject.toml`).
- Install editable (recommended for development):
  - `python -m pip install -e .`
- Optional CPU extras (torch):
  - `python -m pip install -e .[cpu]`
- Cluster-specific deps list: `requirements_cluster.txt`.

## Linting and formatting
- Formatter: Black with line length 120 (`pyproject.toml`).
  - Format a file: `python -m black path/to/file.py`
  - Format the repo: `python -m black .`
- No Ruff/Flake8/Mypy configuration found in the repo.
- If you add new tools, update this file and `pyproject.toml`.

## Tests
- No test framework configuration or `tests/` directory found.
- There is no documented test command in the repo.
- If you add tests later, prefer `pytest` and document:
  - All tests: `python -m pytest`
  - Single test file: `python -m pytest path/to/test_file.py`
  - Single test case: `python -m pytest -k "TestName or test_function"`
- For now, validate behavior by running the relevant script or module.

## Code style and conventions

### Imports
- Standard library first, then third-party, then local imports.
- Prefer absolute imports from `src` for cross-module usage.
- `from __future__ import annotations` is used in core modules; follow it.

### Formatting
- Follow Black defaults with line length 120.
- Use one statement per line; avoid inline multiple statements.
- Use trailing commas in multi-line literals for stable formatting.

### Typing
- Use modern Python typing: `list[...]`, `dict[...]`, `tuple[...]`, `|` unions.
- Annotate public functions and methods.
- Use `Literal` and `Optional` for config-like APIs (see `src/iaf/config.py`).
- Pydantic models use `.model_validate` and `.model_dump` (v2 style).

### Naming
- Modules, functions, variables: `snake_case`.
- Classes: `PascalCase`.
- Constants: `UPPER_SNAKE_CASE`.
- Booleans: `is_*/has_*/use_*` patterns are common.

### Docstrings and comments
- Numpy-style docstrings are used in core modules.
- Document parameters, returns, and raised errors.
- Only add comments for non-obvious logic; avoid noise.

### Error handling and validation
- Use `ValueError` for invalid inputs (common in core modules).
- Assertions are used for shape checks in some utilities.
- Pydantic validators enforce constraints in config models.
- Prefer explicit checks with clear messages over silent failures.

### Data and numerics
- Use NumPy for vectorized operations and array math.
- Use Pandas for tabular data IO and light transformations.
- Use SciPy for fitting and physical constants.
- Avoid unnecessary copies in tight loops unless correctness requires it.

### Plotting and figures
- Matplotlib is the default plotting library.
- Plotting helpers live in `src/plotting.py` and `src/iaf/plotting.py`.
- Use existing helpers (`save_figure`, `FigParams`) instead of ad-hoc settings.

### Configuration
- Simulation configuration lives in `src/iaf/config.py`.
- Prefer YAML configs loaded via `BaseConfig.from_yaml` or `Simulation.from_yaml`.
- Keep config schemas strict; add validation when new fields are added.

### Files and paths
- Use `pathlib.Path` for paths in new code.
- Shared data/figure directories are accessed via `src/files.py` helpers.
- Avoid hard-coded absolute paths.
